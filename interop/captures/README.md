# Captures

Packet captures of our own sessions against the interop harness, made with `interop/capture.sh`
and summarised with `interop/pcapsummary.py`. They record what the stock OpenVPN client and server
put in the plain control headers. The clean-room rule allows observing our own sessions; the
summaries are the readable form.

## stock-2.7.0-reneg

- **Made:** 2026-11-24 on the test host, `interop/capture.sh stock-2.7.0-reneg --reneg-sec 20`.
- **Server:** the harness server (`interop/server.conf`) in the `26.04` image, openvpn
  2.7.0-1ubuntu1.4.
- **Client:** the stock client (`interop/client.conf`) in the same image, with `--reneg-sec 20`;
  50 s of capture.
- **PKI:** generated by `interop/mkpki.sh` for this run; no third-party material.
- **What it shows:**
  - The hard reset and TLS handshake under key ID 0, in plain headers.
  - Two renegotiations, under key IDs 1 and 2, whose control packets do *not* parse as plain
    headers: no ACK list where one is expected, and implausible packet IDs. The stock client
    advertises dynamic tls-crypt (`IV_PROTO=8094`, bit 9 set, read from the server log), and the
    server pushed `dyn-tls-crypt`, so renegotiations run wrapped. A run with `--compat-mode 2.5.0`
    sent the same `IV_PROTO` and was wrapped the same way, so a stock client cannot show a plain soft
    reset. burrow's own client, which does not set bit 9, observes that (spec notes O13).
